⚠️ Why Avoid any + Replacements
⚠️
Why Avoid anyCore Concept
  • Loses autocompletion & compile-time checks
  • Bugs move from compile-time → runtime
  • Hard to maintain in large Angular apps
  • Acts as a "type escape hatch" — disables TS entirely
⚠️ Reserve any only for 3rd-party libs with no type defs. Even then, prefer unknown. 
// ❌ BAD

data.toFixed(2); // Runtime crash, TS stays silent
✅

🔒 any vs unknown — Safety Patterns
🔒
any vs unknownCore Safety
  • any → do anything, no type checks → 💥 runtime errors
  • unknown → must narrow type before use → ✅ compile safety
  • Think of unknown: "Don't know the type yet — validate first"
// ❌ any — silent crash
let data: any = "hello";
data.toFixed(2); // TS allows, crashes at runtime

// ✅ unknown — forces type check first
let data: unknown = "hello";
if (typeof data === "string") {
  console.log(data.toUpperCase()); // ✅ Safe
}
if (typeof data === "number") {
  console.log(data.toFixed(2));   // ✅ Safe
}

🔑 Symbol — Unique IDs
🔑
Symbol — Unique IDsAdvanced
  • Symbol() always creates a globally unique value
  • Same description ≠ same symbol — every call is unique
  • Good for guaranteed in-memory unique identifiers (no collisions)
  • Cannot be serialized to JSON → not for APIs or databases
  • Can be used as object property values or keys
type User = { id: symbol; name: string; };

const users: User[] = [
  { id: Symbol("user"), name: "Alice" },
  { id: Symbol("user"), name: "Bob"  }
];

// Even same description → NOT equal
Symbol("user") === Symbol("user"); // false !

// Find by captured reference (not by value)
const idToFind = users[0].id;
const found = users.find(u => u.id === idToFind);
console.log(found?.name); // "Alice" ✅
⚠️ Symbols are invisible in JSON.stringify() — never use them as IDs for data you send to an API or store in a DB.
🟣
Symbol vs API-safe IDs Advanced
  • Symbol → best for internal, hidden, collision-free logic
  • NOT serializable → ignored in JSON.stringify()
  • Use UUID / string for API + DB (persistent identity)
  • Symbols are perfect for private metadata & framework internals
  • Best practice → combine Symbol + UUID (internal + external)
import { v4 as uuid } from 'uuid';

const INTERNAL = Symbol('internal');

interface Task {
  id: string; // ✅ API / DB safe
  title: string;
  [INTERNAL]?: { // 🟣 internal only
    isDirty: boolean;
    lastUpdated: number;
  };
}

const task: Task = {
  id: uuid(),
  title: 'Build feature',
  [INTERNAL]: {
    isDirty: true,
    lastUpdated: Date.now()
  }
};

// ❌ Symbol removed in API payload
JSON.stringify(task);

// Output → { "id": "...", "title": "Build feature" }
⚠️ Use Symbol only for internal logic. Never use it for API/DB IDs — it disappears in JSON.
💡 Best Practice: UUID/String → external identity Symbol → internal metadata (UI state, flags, caching)

Auth Service Architecture Patterns
  • Token Storage = Save JWT in memory (secure) or localStorage (persistent)
  • Auth State = Use signals or store for global auth state
  • HTTP Interceptor = Automatically add token to requests
  • Refresh Logic = Handle token expiration gracefully
Auth Service (Signal-based)
export interface AuthState {
token: string | null;
user: User | null;
isAuthenticated: boolean;
loading: boolean;
}

@Injectable({ providedIn: 'root' })
export class AuthService {
private http = inject(HttpClient);

// State signals
private authState = signal<AuthState>({
token: null,
user: null,
isAuthenticated: false,
loading: false
});

// Public read-only signals
isAuthenticated = computed(() => 
this.authState().isAuthenticated
);
currentUser = computed(() => 
this.authState().user
);
token = computed(() => 
this.authState().token
);

login(email: string, password: string) {
this.authState.mutate(s => s.loading = true);

return this.http
  .post<{ token: string; user: User }>(
    '/api/login',
    { email, password }
  )
  .pipe(
    tap(({ token, user }) => {
      this.authState.mutate(s => {
        s.token = token;
        s.user = user;
        s.isAuthenticated = true;
        s.loading = false;
      });
      localStorage.setItem('token', token);
    }),
    catchError(err => {
      this.authState.mutate(s => s.loading = false);
      throw err;
    })
  );
}

logout() {
this.authState.set({
  token: null,
  user: null,
  isAuthenticated: false,
  loading: false
});
localStorage.removeItem('token');
}

initializeAuth() {
const token = localStorage.getItem('token');
if (token) {
  this.validateToken(token);
}
}

private validateToken(token: string) {
this.http
  .post<{ user: User }>('/api/validate', { token })
  .subscribe(({ user }) => {
    this.authState.mutate(s => {
      s.token = token;
      s.user = user;
      s.isAuthenticated = true;
    });
  });
}
}
💡 Best Practice: Keep token in memory (sessionStorage), not localStorage for security.

HTTP Interceptor for Auth Angular 15+
  • Automatically add token to all requests
  • Handle 401 (unauthorized) response
  • Refresh expired tokens
Auth Interceptor (Functional)
export const authInterceptor: HttpInterceptorFn = 
(req, next) => {
const authService = inject(AuthService);
const token = authService.token();

// Add token to request
if (token) {
  req = req.clone({
    setHeaders: {
      Authorization: `Bearer ${token}`
    }
  });
}

return next(req).pipe(
  catchError((error: HttpErrorResponse) => {
    // Handle 401 - redirect to login
    if (error.status === 401) {
      authService.logout();
      // Redirect to login
    }
    return throwError(() => error);
  })
);
};

// Register in app.config.ts
export const appConfig: ApplicationConfig = {
providers: [
provideHttpClient(
  withInterceptors([authInterceptor])
)
]
};
Handle Token Refresh
export const authInterceptor: HttpInterceptorFn = 
(req, next) => {
const authService = inject(AuthService);
const router = inject(Router);

return next(req).pipe(
  catchError((error: HttpErrorResponse) => {
    if (error.status === 401) {
      // Try to refresh token
      return authService.refreshToken().pipe(
        switchMap(() => {
          // Retry with new token
          const newToken = authService.token();
          return next(
            req.clone({
              setHeaders: {
                Authorization: `Bearer ${newToken}`
              }
            })
          );
        }),
        catchError(() => {
          // Refresh failed - redirect to login
          authService.logout();
          router.navigate(['/login']);
          return throwError(() => error);
        })
      );
    }
    return throwError(() => error);
  })
);
};
✅ Modern Approach: Use functional interceptors (Angular 15+) instead of class-based.

Role-Based Access Control (RBAC) Authorization
  • Roles = Admin, User, Guest, Editor
  • Permissions = Can read, write, delete

Extend AuthService with Roles
export interface User {
id: number;
name: string;
email: string;
roles: string[]; // ['admin', 'user']
permissions: string[]; // ['read', 'write']
}

@Injectable({ providedIn: 'root' })
export class AuthService {
currentUser = computed(() => 
this.authState().user
);

hasRole(role: string): boolean {
const user = this.currentUser();
return user?.roles.includes(role) ?? false;
}

hasPermission(permission: string): boolean {
const user = this.currentUser();
return user?.permissions.includes(permission) ?? false;
}

hasAnyRole(roles: string[]): boolean {
return roles.some(role => this.hasRole(role));
}
}

CanActivate Guard (Auth Protection) Most Common
  • Protect routes from unauthorized access
  • Return true to allow, false to deny

Functional CanActivate Guard (Angular 15+)
import { CanActivateFn } from '@angular/router';

// Simple auth guard
export const authGuard: CanActivateFn = (route, state) => {
const authService = inject(AuthService);
const router = inject(Router);

// Check if authenticated
if (authService.isAuthenticated()) {
return true; // ✅ Allow access
}

// Redirect to login if not authenticated
return router.createUrlTree(['/login'], {
queryParams: { returnUrl: state.url }
});
};

// Role-based guard
export const adminGuard: CanActivateFn = (route, state) => {
const authService = inject(AuthService);
const router = inject(Router);

if (!authService.isAuthenticated()) {
return router.createUrlTree(['/login']);
}

if (!authService.hasRole('admin')) {
return router.createUrlTree(['/unauthorized']);
}

return true;
};

CanDeactivate Guard (Unsaved Changes) UX Safety
  • Ask before leaving route with unsaved changes
  • Prevents accidental data loss
  • Returns boolean or Promise/Observable
Implement Deactivate Interface
export interface CanComponentDeactivate {
canDeactivate(): boolean | Promise<boolean>;
}

@Component({
selector: 'app-form-edit',
template: `
<form [formGroup]="form">
  <input formControlName="name" />
  <button (click)="save()">Save</button>
</form>
`
})
export class FormEditComponent 
implements CanComponentDeactivate {

form: FormGroup;
originalValue: any;

canDeactivate(): boolean {
// Allow navigation if form not dirty
if (!this.form.dirty) {
  return true;
}

// Ask user if they want to leave
return confirm(
  'You have unsaved changes. Leave anyway?'
);

Memoization in JavaScript Performance
  • Caches function results to avoid recomputation
  • Works best for pure functions (same input → same output)
  • Improves performance for expensive operations
  • Uses closure or Map to store previous results
// Basic memoization
function memoize(fn) {
  const cache = new Map();

  return function (...args) {
    const key = JSON.stringify(args);

    if (cache.has(key)) {
      return cache.get(key); // return cached result
    }

    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

// Use case: expensive calculation
function slowSquare(n) {
  console.log('Computing...');
  return n * n;
}

const memoSquare = memoize(slowSquare);

memoSquare(5); // Computing... → 25
memoSquare(5); // cached → 25 (no log)

  return res.json();

  constructor() {
    const saved = localStorage.getItem('theme');

    if (saved) {
      this.theme.set(saved as any);

    });
  }

    this.theme.update(t =>
      t === 'light' ? 'dark' : 'light'
    );
  }
}

How does Spring Boot fit in a Microfrontend (Angular Sales App) architecture?
"In a microfrontend architecture, Angular applications act as UI layers that communicate with backend services via REST APIs.

The typical request flow is:

Angular Microfrontend (UI) → Controller (REST API) → Service (Business Logic) → Repository (Data Access) → Database

Each layer has a clear responsibility:
- Controller: Handles HTTP requests/responses
- Service: Implements business rules
- Repository: Interacts with database using JPA (Java Persistence API)
- Database: Stores persistent data

Example: Sales dashboard fetching orders → Angular calls /api/orders → Spring processes → DB returns data → UI renders table.

Key Insight: Spring Boot is the engine powering your microfrontend UI."
How do Virtual Threads (Project Loom - Java 21) improve scalability in Spring Boot applications?
"Virtual Threads (from Project Loom) are lightweight threads managed by the JVM instead of the OS.

Traditional model: 1 thread = ~1MB memory → limited scalability.
Virtual threads: Millions of threads with minimal memory overhead.

This allows handling massive concurrent I/O operations (like API calls, DB calls) without blocking system resources.

Impact on Spring Boot:
- Simplifies concurrency (no need for complex async/reactive code)
- Improves throughput for I/O-bound applications

Use Case: High-traffic sales APIs handling thousands of concurrent users.

Key Benefit: Write simple synchronous code with massive scalability."
When is parallelStream() a bad choice in Java Streams API (Application Programming Interface)?
"parallelStream() uses ForkJoinPool (shared thread pool based on CPU cores).

It becomes inefficient when:
- Performing blocking I/O (database/API calls)
- Working with shared mutable state (synchronization overhead)
- Small datasets (<1000 elements)

Bad Example: Fetching users from DB inside parallel stream (threads get blocked).

Good Example: CPU-intensive tasks like mathematical computations.

Risk: Thread starvation and degraded performance.

Rule: Use parallelStream ONLY for CPU-bound, stateless operations."
How does @Transactional (Transaction Management) work internally in Spring?
"@Transactional enables declarative transaction management using AOP (Aspect-Oriented Programming).

Spring creates a proxy (CGLIB or JDK dynamic proxy) around the service bean.

Flow:
Client → Proxy → Transaction शुरू → Method execution → Commit/Rollback

Critical Limitation:
Internal method calls within the same class bypass the proxy → NO transaction applied.

Rollback Rule:
- Rolls back on RuntimeException
- Does NOT rollback on checked exceptions by default

Best Practice: Keep transactional methods in separate service classes.

Common Bug: Transactions silently not working due to self-invocation."
How do you troubleshoot a 100% CPU spike in a Java Spring Boot application?
"Step-by-step debugging approach:

1. Identify high CPU threads → top -H
2. Convert thread ID to hex
3. Take thread dump → jcmd <pid> Thread.print
4. Analyze stack trace

Common Causes:
- Infinite loops
- Deadlocks
- Blocking I/O
- Excessive parallel processing

Real Example: Order processing loop stuck in retry logic.

Goal: Identify the exact line of code causing CPU burn."
What is the difference between @Fetch(FetchMode.JOIN) and @EntityGraph in JPA (Java Persistence API)?
"Both are used to solve the N+1 query problem.

@Fetch(FetchMode.JOIN):
- Global strategy defined on entity
- Always performs JOIN → can lead to over-fetching

@EntityGraph:
- Query-level control
- Fetch only required associations per use case

Recommendation: Prefer @EntityGraph for flexibility and performance.

Use Case: Fetch users with department only when needed.

Benefit: Avoid unnecessary database load."

What is HATEOAS (Hypermedia As The Engine Of Application State) and when should you use it?
"HATEOAS is a REST constraint where API responses include links to related actions.

Avoid When:
